# Working material

Design conversations, adoption reviews, research comparisons and superseded roadmaps — the material the committed designs were distilled *from*. Kept because the reasoning is worth keeping; deliberately not part of the documentation site, because it records how decisions were reached rather than what was decided. The distilled results live in [`docs/`](../docs/), which is the site.

Two of these are specifications rather than conversations, and both have been built past their first phase — so a reader picking them up should know which parts are now code and which are still design. [Persistent components and online change](source-rpc-online-change-design/source-rpc-online-change-design-spec.md): Phases 1 to 3 are `@source-repo/continuity` — snapshots and held-state migration, then the managed runtime, consistent capture and the obligation manifest, then shadow activation, ownership epochs and fenced replacement — along with the portable form and the C# reader that Phase 4 turns on. What is not built is Phase 4's journal and replay-assisted recovery, which is what `failed-after-commit`'s *recover forward* would need to be a procedure rather than an instruction. [Node live diagnostics](source-rpc-node-live-diagnostics-design/source-rpc-node-live-diagnostics-design-spec.md): Phase 1, source-linked props and state, is `@source-repo/diagnostics` and the console's source view. Phase 2 is built as far as its telemetry — a variant can be proved a derivative (`admissibleVariant`, with the strip in `@source-repo/rpc-cli`), generated (`instrumentSource`), given somewhere to write (`RpcProbeSink`), and swapped in and out over continuity's `handOver`, which is section 16 step for step. Its telemetry is built too: an observation session with the design's twelve permissions, a deadline, a latest-value table published as state, an ordered trace as an event for a session permitted to keep one, and classified values withheld at capture rather than in the editor. Tracepoints are built too, with their conditions compiled into the derivative and checked against a constrained grammar rather than evaluated at runtime. Of Phase 3, safe-boundary breakpoints are built — the probe asks, the running handler finishes, and the barrier stops the next unit of work — along with the controller lease, the pause deadline and its three expiry actions, which is five of that phase's seven acceptance criteria. Exact pause and stepping are not, and need the worker the feasibility note measures. Those are advertised as `false` rather than omitted, and the capability set is now derived from what a host actually wired rather than declared, so a node that has no coordinator says so. The specs are unedited — their status lines describe what was ready to build when they were written, not what has since been built.

Also here: [what an exact pause would cost](exact-pause-feasibility.md) — a working pause gate, measured, with the limits established before anything was built on it. The finding that decides the shape of Phase 3 is that a parked thread freezes everything sharing it, so a pause scope of *one component* means a worker per component, and the expensive part is not the gate but moving component logic off the transport's thread in `@source-repo/rpc`.

Also here: field-trial feedback, starting with [the first fresh-agent session](session-feedback-2026-08-01.md) — a Claude with no prior knowledge of the project working the network through the MCP server, whose findings were filed into Linear.
